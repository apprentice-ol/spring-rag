# 设计：dev-loop 健康开发循环（程序员式流程）

> 状态：设计完成，待用户确认后落地
> 日期：2026-10-11
> 背景：run `2026-10-11-1701-docker` 阶段 3 暴露流程结构性问题（批量跑批 + CLI 汇总误导 + 豁免掩盖 + 脏数据自我维持），用户定调：**整个流程要像正常程序员开发一样——编写、编译、测试、修复、重新编译、重新测试、记录**。

## 一、问题诊断（为什么现有流程不健康）

| # | 症状 | 根因 |
|---|---|---|
| 1 | 批量跑批 81 用例只看汇总数字，过程黑盒 | 测试被当成"打卡"而非"验证"——丢失逐例过程价值 |
| 2 | CLI 表格显示 1 请求 0 失败 exit=0，json 实为 81 用例 7 失败 | 判定链依赖了错误的工具输出层（已修：以 json 报告为准） |
| 3 | 7 失败靠"豁免"续跑，从上午拖到下午没人修 | 豁免无修复责任、无期限，变成无限期合法带红 |
| 4 | "冒烟测试" pipeline 是上午跑批创建的脏数据，每次跑批必 500 | 用例不自清理（固定名重复创建），流程自己制造失败 |
| 5 | 上传 ×4 用例缺 fixture，从未真正执行过上传 | 用例只保证"打了请求"不保证"测了功能"，81 是虚数 |
| 6 | 接口重名返 500 裸堆栈、S3 不存在返 500 | 异常路径无设计：成功/异常/失败三档路径未区分处理 |

**结论**：不健康不是单点 bug，而是流程缺了程序员开发循环的核心动作——**逐单元验证（响应+日志双向看）、异常即停即修即重验、全程记录**。

## 二、设计理念

**模拟一名健康程序员的工作方式**：

```
        ┌──────────────── 单元循环（逐功能点）────────────────┐
        │                                                        │
 编写 → 编译 → 启动/重启 → 自测（亲调 + 看响应 + 盯日志）          │
   ↑                    │                                       │
   │                    ├─ 异常 → 归因 → 提出（用户确认）→ 修复 ──┘
   │                    │        （修代码/改用例/改需求设计）
   │                    ↓
   │              本单元绿 → 记录 → 下一单元
   │                    ↓
   │              全部单元绿 → 整体回归（批量兜底）→ 联调 → 提交 → 打包 → 部署 → 验收报告
   └── 修复动作回流（改了代码就回到编译）
```

五条铁律：
1. **单元化推进**：变更拆成可独立验证的小单元（一个接口/一组关联接口/一个页面交互），逐单元走完循环，不攒大批
2. **预期有权威载体，编译通过不算数**：每接口的三档预期（成功 2xx+关键结构 / 异常 4xx+友好 message / 失败兜底统一错误体不裸堆栈）持久化于**需求文件夹**（pipeline.yml `testing.expectations_dir`，缺省 `docs/requirements/`，按域一文件）。测试先读它——无条目先补写预期再测（预期文档本身是测试的产出物）；**实测 ≠ 预期**时三去向：代码错→修代码 / 预期文档错或缺→修文档（提出+用户确认）/ 需求歧义→**询问用户，答案回写文档**。执行结果永远对照计划或需求裁决，不凭感觉
3. **双向对账**：看响应（对前端）+ 看日志（对系统）——吞异常返 200 的接口只有日志能暴露
4. **异常即停即修即重验**：发现异常当场归因（用例/代码/需求三分类）→ 提出给用户 → 确认后修 → **重新编译 → 重启 → 重测本单元** → 绿了才推进
5. **全程记录**：每单元每轮的请求/响应/日志/结论/异常处置全部落台账，可回溯

## 三、流程阶段设计

### 阶段总览（改造后 dev-loop）

| 阶段 | 内容 | 与现状差异 |
|---|---|---|
| 0 预检 | 依赖/能力矩阵/代码锚点/台账 | 不变 |
| 1 编译 | build skill（IDEA + inspections） | 不变（也是每轮修复后的"重新编译"入口） |
| 2 启动 | IDEA/命令行 + ready_log | 不变（也是每轮修复后的"重启"入口） |
| **3 接口测试** | **单元循环 ×N + 收尾整体回归** | **重构**：默认深测逐单元，批量只做收尾兜底 |
| **4 前后端联调** | **页面/交换单元循环** | 同理念：逐变更点验证 + console/network 对账 |
| 5 提交 | 测试结论明确才提交 | 不变 |
| 6-8 打包/部署/验收 | 现有机制 | 不变 |

### 单元循环细则（阶段 3 的核心）

**进入单元前：读需求文件夹**（预期的权威载体，pipeline.yml `testing.expectations_dir`，缺省 `docs/requirements/`）：
```
### <METHOD> <path> — <一句话语义>
- 成功：2xx + 响应含 <关键字段/结构>
- 异常：<错误输入> → 4xx，message 含 <友好提示>
- 兜底：未知错误 → 统一错误体（不裸堆栈）
- 来源/变更：<日期 或 引用的计划/需求文档>；改预期须用户确认
```
- 该接口**有条目 → 按条目测**；**无条目 → 先补写条目（提出给用户过目）再测**——预期文档随测试逐步长全，成为活文档
- 实测 ≠ 预期：修代码 / 修条目（用户确认）/ 询问（答案回写条目）

**循环体**（每单元）：
1. **记日志锚点**：后端日志文件 offset / `docker logs --since <ts>`（保证能取本单元增量日志）
2. **执行**：curl 亲调（首选——直观看响应体）或 `apifox run --test-case`（用例在套件时）；SSE 用 curl -N
3. **三向核对**：
   - 响应档位 vs 预期清单（状态码 + 关键结构）
   - 响应语义（字段值与业务预期对得上，不是"有返回"就算过）
   - 增量日志（无未预期 ERROR；`未捕获异常` 一票否决）
4. **异常处置**（触发即停）：
   - 归因：`用例问题 / 代码 bug / 需求设计偏差`
   - **提出**：向用户报告 现象 + 根因 + 建议——需求/设计类**必须用户拍板**才改
   - 修复 → 阶段 1 重新编译 → 阶段 2 重启 → **重测本单元**（不是重跑全部）
5. **本单元绿 → 记录 → 下一单元**；一轮 run 测不完是常态，台账记进度（"深测到第 N 单元"），下会话续跑

**联调单元循环（阶段 4，与阶段 3 同构）**：接口符合预期后，联调照同样流程——单元 = 一个页面/一组关联交互；预期先行读 `web-<页面>.md` 条目（成功：操作→呈现含关键数据 / 异常：4xx→友好提示不白屏 / 兜底：断网·5xx→错误态）；亲测三向对账（渲染 vs 预期 + console 无未预期 error + network 请求↔渲染数据对账）；异常即停（归因：前端代码/后端接口/预期条目 → 提出 → 修 → 前端热更或后端 build 重启 → 重测本单元）；单元绿记录推进，收尾整体过 e2e_cases。记录落 `stages/4-web/<单元>.md`。

**收尾（全部单元绿后）**：
1. **数据自清理检查**：本 run 测试创建的数据（pipelines/datasets 等）清理或改随机名，保证下次跑批不带脏数据
2. **整体回归**：批量套件跑一遍（json 报告判定）；**零未处置失败**才过——豁免须用户当次确认 + 修复计划 + 期限
3. 通过 → 阶段 4

### 记录设计（贯穿全程）

```
runs/<runId>/
├── summary.md                    # 总台账 + 单元进度表 + 异常处置登记表
├── stages/
│   ├── 3-api/
│   │   ├── <NN>-<单元名>.md      # 每单元一份：预期清单/实测/日志摘录/结论
│   │   └── regression.md        # 收尾整体回归报告
│   └── ...
└── artifacts/                    # 截图/大日志
```

**单元记录模板**：
```markdown
# 单元 NN · <名称>
- 预期：成功 … / 异常 … / 兜底 …
- 实测：`<请求>` → `<响应关键行>`（原文粘贴）
- 日志增量：`<ERROR/WARN 摘录或"无异常">`
- 结论：✅ / ❌（→ 异常登记 #K）
```

**异常处置登记表**（summary 内，豁免的前置形态）：
```markdown
| # | 单元 | 现象 | 归因 | 提出 | 用户决策 | 修复 | 重验 |
|---|---|---|---|---|---|---|---|
| 1 | POST /ingestion/pipelines | 重名 500 裸堆栈 | 代码（缺 DuplicateKey 兜底） | ✅ 已报 | 修 | GlobalExceptionHandler +409 | ✅ 409 |
```
- 登记表条目闭环（修复+重验 ✅）才能从"异常"变"已解决"
- **豁免 = 登记表里用户决策为"暂不修"的条目**：必须带修复计划 + 期限（≤5 run），超期阻断 PASS

## 四、工具与用例配套

1. **日志对账三通道**（锚点 → 增量 → 过滤 ERROR 摘录；IDEA MCP 无流式订阅 API，文件轮询即用——2026-10-11 实测验证）：
   - **IDEA 启动（MCP 起）**：`execute_run_configuration` 返回的 `fullOutputPath` → 文件 offset 增量读（注意：返回体的 `output` 快照字段会截断，文件才是全量）
   - **IDEA 启动（用户手动起）**：按 mtime glob `%LOCALAPPDATA%\JetBrains\IntelliJIdea<ver>\tmp\ij_run__<配置名>_*.log` 取最新
   - **docker 场景**：`docker logs --since <时间戳> <service>`
   - 后续可脚本化：记 offset → 取增量 → 过滤 `ERROR|未捕获异常` → 摘录进单元记录
2. **需求文件夹机制**（`docs/requirements/`，scaffold 提供 README 模板 + pipeline-init 骨架可选取）：
   - 按域一文件（`api-ingestion.md` / `api-storage.md` / `web-<页面>.md`…），每接口/交互一条目（格式见 §三）
   - 与测试的关系：深测的 oracle（先读后测）；与异常登记表的关系：登记表记录处置过程，需求条目沉淀最终口径
   - pipeline.yml 字段 `testing.expectations_dir` 声明位置（缺省 `docs/requirements/`）
3. **用例生成器**（apifox-gen-cases.py）配套改造：
   - name 类占位值改 `smoke-<时间戳>`（消灭固定名脏数据）
   - 用例注释标注档位（默认成功档；异常档深测时手工补）
4. **异常路径补测**：本次实证三处待补——DuplicateKey→409、S3 NoSuchKey→404、上传 fixture 机制（`api.fixtures_dir` + multipart 用例）

## 六、补充机制（2026-10-11 二轮定稿）

1. **seed 前置数据**：条目"前置"字段声明依赖；实现两条路——IDEA MCP `execute_sql_query`（agent 亲造亲验，深测默认）/ Apifox 测试场景（多步骤编排+响应变量提取传递，CLI `-t` 支持，沉淀可重复资产用）
2. **抽检制回归**：默认收尾回归只跑抽检集（条目 `抽检: Y`：每域 ≥1 成功路径 + 全部已知异常路径代表，预计 10-15 条）；**全量套件仅发版前**——不再每次 81 用例全跑
3. **横切修复重测升级**：修横切面（全局异常/拦截器/公共组件）→ 重测范围从本单元升级为受影响域冒烟或抽检集回归
4. **提出分级**：低风险（方案明确的代码 bug）→ 报告即修、登记留痕；高风险（需求歧义/对外行为改变/数据删除/改预期条目）→ 必须用户批准——防逐例询问瘫痪
5. **条目状态跟踪**：`状态: ✅ 已验证@<runId> / ⏳ / ❌` ——需求文件夹即活覆盖清单，grep 即覆盖率
6. **提交粒度**：按逻辑单元小步提交，不攒大 commit；单元绿+登记闭环可做 commit 锚点
7. **DDL 联动**：修复涉及表结构 → 跑结构对齐脚本 + 重启验证（防本地绿部署炸）
8. **已知噪声基线**：无害 WARN/ERROR 入需求文件夹 README 基线节，日志对账自动排除；新噪声先判定再入
9. **边界声明**：单元循环覆盖**功能正确性**；并发/竞态/性能/安全不在其中（靠全量回归、eval 体系与后续专项）——单元全绿 ≠ 系统无懈可击
10. **环境纪律（防混防串，最高优先级）**：run 级锁定 target 并全程 `[env: <target>]` 标注，中途不隐式切换；高危分级门——local/docker 低危、dev 部署与数据操作须确认、**prod 双重确认+宣读目标与影响**；配置隔离（每环境独立 .env，.env.example 唯一模板源，真实值不跨环境流转）+ 配置同步检查（新增变量进部署清单，远程启动失败先查缺失变量）；**数据操作红线——测试写操作（seed/清理）仅限 local/docker 的库，dev/prod 数据库只读**（动手前核对 JDBC 连接指向）

## 七、验收标准

流程健康 = 以下全部成立：
- 任意时刻中断，台账能回答"测到哪、异常哪些、哪些已闭环"
- 跑批可重复执行且**不因上次跑批的数据而失败**（自清理）
- 豁免清单只减不增（每项有期限且在消化）
- 每个接口的异常路径有断言保护（4xx 友好提示，不裸 500）
- 需求文件夹条目覆盖率可见（✅/⏳/❌ 统计），抽检集随异常路径的修复动态调整
